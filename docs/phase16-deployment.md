# Phase 16 · Deployment and recovery

## Provision staging first

1. Provision a private network with Linux Docker Compose, managed PostgreSQL 17, Redis, a private S3-compatible bucket, DNS, and a TLS ingress. Use separate hosts, credentials, buckets, and notifications configuration for staging and production. Select regions and subprocessors after privacy review.
2. Block direct access to the API, PostgreSQL, Redis and ClamAV. The supplied Compose exposes only Caddy ports 80 and 443. Restrict database and broker ACLs and use encrypted connections. Use `sslmode=verify-full` with the deployment CA and `rediss://` with certificate validation. Give the API a schema-scoped runtime role, give the migration job a separate role with DDL rights, and keep backup and erasure credentials separate. Store secrets in your infrastructure secret manager. The app reads environment variables or files in `/run/secrets`. Env values take precedence.
3. Prepare the Compose shell or CLI env with `COURTASSIST_DOMAIN`, `COURTASSIST_RELEASE`, and `COURTASSIST_CONFIG`. Copy the backend `.env.example` into a private file outside source control and restrict its permissions. Use `APP_ENV=staging` or `production`, set the exact DNS hostname in `TRUSTED_HOSTS`, configure `DATABASE_URL`, `REDIS_URL`, a random `JWT_SECRET_KEY`, and explicit HTTPS origins in `CORS_ORIGINS` only if a browser client is served. Leave CORS empty for a mobile-only deployment. Set `PRIVATE_STORAGE_DIR=/app/private_uploads`. The production image runs as UID 10001. Ensure the profile volume is writable by that user, and back it up separately. Replace example values with actual deployment configuration.
4. Configure `DOCUMENT_S3_BUCKET`, `DOCUMENT_S3_REGION`, and narrowly scoped S3 credentials. Block public access, enable bucket encryption and versioning, and deny non-TLS requests. Put object versions and backup copies behind separate roles. Grant the runtime only the vault read/write permissions it needs. Use a short lifecycle on `documents/staging/` including noncurrent versions. The erasure role also needs version listing and deletion. Use `CLAMAV_HOST` and `CLAMAV_PORT` for a private clamd service with current signatures and `StreamMaxLength` at least `DOCUMENT_MAX_BYTES`. A scan failure leaves the upload in inaccessible staging. Validate with a clean synthetic file and EICAR in staging. Apply per-practice upload quotas and provider-side bucket budget alarms.
5. Configure SMTP and an HTTPS reset page before offering password recovery. Leave FCM and AI off until configured and reviewed. Keep FCM credentials and AI keys server-side. For FCM follow [Phase 13](phase13-notifications.md). For AI follow [Phase 14](phase14-ai.md), constrain egress to reviewed provider destinations, and set provider budget limits. AI cost reporting is an estimate and the configured per-user job limits are the app-side control.

## Deploy the backend

Run the commands from `court-assist-backend` on the staging host. These commands are for an operator to execute.

```sh
docker compose -f compose.production.yml config --quiet
docker compose -f compose.production.yml build
docker compose -f compose.production.yml --profile maintenance run --rm migrate
docker compose -f compose.production.yml up -d
docker compose -f compose.production.yml exec -T api python -m ops.probe
```

Inject the DDL role's `DATABASE_URL` only into the migration job. Revision `0021_release_controls` adds an account erasure receipt table, a payment request digest and a partial session lookup index. Take a verified backup first and schedule the migration for a low-traffic period. Keep the additive migration on application rollback unless the rollback plan explicitly addresses payment replay and erasure receipts. Restore a backup to a new database if schema recovery is needed. Do not drop audit receipts or overwrite a live database during rollback.

The stack runs two Uvicorn workers, dedicated OCR and notification workers, and one Celery Beat. Start optional AI with `--profile ai`. Deploy all workers together with the API. Drain OCR tasks still on the former default queue with the old worker before cutover, or requeue pending OCR rows through a reviewed operator procedure. The API's trusted proxy address must match the configured ingress address. Keep that network isolated. For an alternate managed ingress, configure the exact trusted proxy addresses and disable access logging that records query strings. The app body cap is 8 MiB by default, with a separate direct-to-vault file limit. Configure ingress at or below the application cap.

Check HTTPS `/api/v1/live` for liveness and `/api/v1/ready` for PostgreSQL, expected Alembic head and Redis. Validate credentials with a synthetic authenticated workflow and a signed upload, pin, and download. Test deployment-user erasure with synthetic records only. Check OTP expectations explicitly. The app currently uses password sign-in and single-use emailed reset links, and has no OTP sign-in.

## Monitor and respond

- Collect structured `courtassist.http` logs. Chart request counts, 5xx rate and p95 duration by route template. Alert initially at 2% 5xx over 5 minutes or p95 over 750 ms for normal reads over 15 minutes. Tune from staging traffic. Track repeated 413 and 429 responses separately. Request IDs correlate operational events. Never ingest request bodies, query strings, bearer headers, signed URLs, database parameter values or Celery message arguments.
- Check `/ready` externally once a minute. Run `python -m ops.probe` privately on a schedule for PostgreSQL, Redis queue depth and storage availability. Check Celery worker presence with `celery inspect ping` and worker-specific routing. Alert on sustained queue backlog, missing scheduler or worker, repeated OCR failures, failed sync outcomes, and failed backups. Use a periodic synthetic job to verify progress because a responsive Redis broker does not establish worker health.
- Monitor the existing AI job status and notification attempts without exporting their payloads. Set alerts for PostgreSQL connection saturation, statement timeouts, slow queries, Redis memory/evictions and storage errors. The supplied code emits operational telemetry. Configure collection, dashboarding, paging, and Android crash reporting in the actual environment after reviewing provider data handling.
- Route a failed deployment to the on-call operator. Pause writes if integrity is uncertain, preserve evidence with restricted access, revoke compromised sessions or credentials, and follow the incident runbook. Do not put legal content in incident tickets. See [privacy and incident handling](phase16-privacy.md).

## Encrypted backups and recovery

Target a **24-hour RPO and 8-hour RTO** for the initial setup, subject to a completed restore drill. Managed PostgreSQL point-in-time recovery can shorten the database RPO. Coordinate database, vault and profile storage recovery to avoid restored metadata referring to a missing file.

- Schedule `bash ops/backup-postgres.sh` nightly with `PGSERVICE`, `BACKUP_DIRECTORY` and the public `AGE_RECIPIENT`. Configure a read-only backup role and protected `pg_service.conf` and `.pgpass` or equivalent secret injection. Run the temporary directory on an encrypted volume, transfer only the encrypted output to a private backup target, and keep the age private key in a separate recovery account. The script checks that the archive catalog can be read before encryption. Schedule a restore test to verify the actual bytes.
- Proposed retention is 14 daily and 8 weekly snapshots, with explicit lifecycle rules on the backup target and separate source-bucket version retention. Test encrypted profile-volume snapshots. Review retention with the practice and verify that backup copies and storage versions have defined expiry.
- To restore, provision an isolated database, decrypt the chosen archive with `age --decrypt -i <key> -o <archive> <backup>`, and run `pg_restore --exit-on-error --no-owner --no-privileges -d <isolated-db> <archive>`. Restore vault and profile copies privately. Reapply completed account erasures and verify record counts, migration head, credentials, sample signed downloads and finance totals. Record restore time and last recovered write before switching traffic. Run a staged restoration before the first launch and monthly thereafter.
- A local drill ran the backup script, decrypted the result with a disposable key, and restored the exact archive into an isolated PostgreSQL 17.11 database. Production scheduling, storage versioning, and recovery objectives still need verification against the provisioned infrastructure.

## Android build and store handoff

Use Node 24, the locked dependencies and Expo SDK 58. Preserve `in.courtassist.advocate` and seed EAS versioning from the highest existing Android versionCode if an application already exists. The supplied EAS profiles produce an internal APK and a production AAB. Configure a separate HTTPS `EXPO_PUBLIC_API_URL` for each profile. Keep signing keys and `credentials.json` out of source control and manage the upload key through the authorized account. If FCM is enabled, configure the matching Firebase Android file with an EAS file variable.

After the authorized EAS project and signing setup, use `npx eas-cli@latest build --platform android --profile preview` for device verification and `npx eas-cli@latest build --platform android --profile production` for the AAB. Inspect the merged manifest and the signed artifact. Test fresh install, an upgrade over the prior signed build, authorization on private deep links, camera scan, PDF creation and file sharing, private vault transfers, Malayalam rendering, notification permission and delivery, background sync, airplane mode, reconnect, process restart and sign-out. A starting Android smoke flow is in `court-assist-mobile/.maestro/release-smoke.yaml`. Provide synthetic test credentials to Maestro through local env injection. Verify icon and splash appearance on the device.

Before a Play release, complete Data safety, target SDK and permissions review, privacy-policy URL, the account deletion web resource, signing and review instructions. Upload through the authorized operator after approval. Keep the signed bundle checksum and release manifest with the release record.
